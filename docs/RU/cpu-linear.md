# Первый C-модуль GEMV/GEMM

[English](../EN/cpu-linear.md)

**Статус выделения:** страница описывает сохранённый прототип с FP32-входами и последовательным накоплением FP64. Побитовый контракт остаётся для проверки регрессий; он не задаёт точность всех будущих форматов. [Граница библиотеки и целевые форматы](architecture.md) определяют дальнейшую реализацию.

В `src/backend/cpu/` в Velri-lib появился самостоятельный **внутренний CPU-кернел линейного
слоя**. Он вычисляет `Y = X × Wᵀ + bias`: одна входная строка означает GEMV,
несколько — GEMM. Это проверенный компонент будущего C-движка. Граф вычислений,
пул работников, публичный API приложения и Vulkan-бэкенд этот модуль не реализует.

## Сборка и проверка

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_COMPILER=clang
cmake --build build
ctest --test-dir build --output-on-failure
```

Нужны CMake 3.21 или новее и Clang 18+ либо GCC 14+ в режиме C23.
При настройке проверяется, что компилятор принимает `-std=c23`.
Зависимости из сети не скачиваются. Работающей библиотеке не нужны Rust и
LLVM. Clang использует LLVM при компиляции; GCC тоже собирает тот же C-код.

`VELRI_CPU_MULTIVERSION=OFF` оставляет только базовый вариант. При включённой
опции на x86-64 также собираются варианты AVX2/FMA и AVX-512F/FMA. Перед выбором
проверяется поддержка процессором и ОС. Сам диспетчер использует базовые
инструкции. `AUTO` выбирает самый широкий доступный вариант. Это не автотюнер
и не обещание лучшей скорости на любом процессоре.

Тот же алгоритм собирается для ARM64. Локальные проверки включают ARM64 под
QEMU: это проверка корректности, а не скорости на настоящем ARM. Windows и
Android остаются целевыми платформами, но сборки этого первого модуля на них
ещё не проверены. CI включает обычный Linux, санитайзеры, сборку только базового
варианта и Linux ARM64 под QEMU.

## Что означает «одинаковый результат»

Каждый выход вычисляется в строго заданном порядке:

1. Начать с аккумулятора FP64, равного `-0.0`.
2. По возрастанию индекса K перевести два входных FP32 в FP64, перемножить
   и добавить произведение в этот аккумулятор.
3. После всей суммы добавить bias в FP64, а при его отсутствии — `+0.0`.
4. Один раз округлить результат до FP32.

Оптимизированный код должен совпадать с независимым эталоном **побитово**.
Допуска по погрешности нет. Нельзя делить сумму по K на независимые части или
хранить промежуточную сумму в FP32. Тесты включают знаковые нули, субнормальные
числа и переполнение. Вызывающий код должен использовать округление к ближайшему
с выбором чётного при равенстве, сохранение субнормальных чисел без обнуления и
отключённые ловушки ошибок арифметики. Кернел не меняет настройки арифметики
вызывающего потока; флаги исключений не входят в контракт результата.

Результат NaN всегда имеет биты `0x7fc00000`. Так его представление одинаково
между вариантами. Это явное уточнение неопределённых битов NaN старого
Rust-эталона: Rust не обещает их переносимость или детерминированность.
Мы **не** заявляем сохранение прежнего payload NaN.
[Документация Rust об арифметике](https://doc.rust-lang.org/std/primitive.f32.html#nan-bit-patterns).

Простой C-эталон с обычными строками весов находится в `tests/cpu/reference.c`.
Он не использует упаковку и арифметические функции быстрого варианта. Обе
реализации также сверяются с сохранённым бинарным результатом неизменённого
Rust-эталона. Происхождение и хеш этой выборки описаны в
`tests/cpu/fixtures/README.md`.

Прежние быстрые FP32-кернелы проверялись с допуском по погрешности и не выполняют
новое требование точного совпадения. Их исторические TFLOPS нельзя выдавать за
скорость этой C-реализации.

## За счёт чего ускоряется кернел

Общий исходник — `linear_kernel.c`. CMake компилирует его с разными размерами
плиток и наборами инструкций, затем создаёт таблицу вариантов. Небольшие
арифметические части AVX2 находятся в `linear_avx2.h`; API, упаковка и правила
вычисления общие. Переносимый C-путь также собирается для ARM64. Проверок
названия процессора внутри арифметики нет.

SIMD вычисляет разные выходные признаки одновременно. Для каждого выхода
сохраняется исходный порядок K. Полное разворачивание короткого цикла по
столбцам позволяет компилятору держать суммы в регистрах, не записывая их
на стек на каждом шаге.

Здесь FMA может объединить умножение и сложение FP64 без изменения конечных
результатов: у каждого FP32 не больше 24 значащих бит, поэтому произведению
нужно не больше 48 бит. Оно точно помещается в 53 бита FP64; диапазона
экспоненты тоже хватает. Эталон сохраняет отдельные умножение и сложение,
быстрый вариант может их объединить. Это не разрешает менять порядок суммы
или переходить на FMA в FP32.

AVX2 GEMV загружает четыре FP32-веса сразу в вектор FP64. Это убирает лишние
широкие загрузки и извлечение половин вектора, которые GCC создавал из исходного
скалярного C-цикла. Та же функция обрабатывает нечётную строку GEMM. При C=32,
K≤2048 и хотя бы восьми выходных плитках на вызов GEMV сначала расширяет вход
в ограниченный буфер на стеке размером 16 КиБ. Остальные размеры читают исходный
вход напрямую. Копирование входит во время исполнения, буфер принадлежит
только текущему вызову, а подготовленные веса остаются прежними.

Основной AVX2-путь GEMM обрабатывает три строки и шестнадцать столбцов. Внутренний
цикл использует двенадцать регистров сумм, три регистра входов и один регистр весов.
Небольшая ассемблерная функция закрепляет это распределение: в автоматически
собранном цикле 3×16 компилятор записывал одну сумму на стек на каждом шаге K.
Обход матрицы остаётся на C. Он объединяет до 24 входных строк и 128 элементов K,
повторно используя участок весов размером 16 КиБ. Частичные суммы FP64 занимают
6 КиБ, временные расширенные входы — 3 КиБ; ещё небольшой буфер нужен для остатка
строк. Суммы переносятся между участками K без округления в FP32; bias добавляется
один раз после всего скалярного произведения.

Узкие плитки, короткий K и другие ISA сохраняют общий путь с парами строк.
Все пути обрабатывают неполные плитки и требуют только естественного выравнивания
float. Завершение с bias и без него разделено: при отсутствии bias больше нет
ненужных маскированных загрузок. Тесты проверяют отмену больших чисел на границах K,
границы групп строк, особые значения и недоступные защитные страницы. Одни лишь
санитайзеры не проверяют обращения к памяти внутри ассемблера.

## Подготовка и память

В `include/velri_lib/linear.h` определены три операции:

| Операция | Задача |
| :--- | :--- |
| `velri_linear_query` | Проверить M/K, выбрать доступный вариант и плитку, сообщить размер упаковки |
| `velri_linear_pack` | Один раз переставить W в предоставленный вызывающим кодом буфер |
| `velri_linear_run` | Проверить представления данных и выполнить вычисление с готовой упаковкой |

W содержит M строк по K значений FP32. Порядок после упаковки:
`[плитка столбцов][K][столбец внутри плитки]`. При ширине плитки C элемент
`(c, i)` находится по индексу `(c / C) * C * K + i * C + c % C`. Неиспользованные
столбцы последней плитки заполнены нулями. Нужная ёмкость —
`ceil(M / C) * C * K` значений float.

Выбранная плитка хотя бы один раз помещается в M. Поэтому упаковка содержит
меньше удвоенного фактического числа весов; при M=1 — ровно K значений.
План учитывает всё дополнение нулями. Веса остаются FP32, копии в FP64 нет.
После упаковки исходные W можно освободить, но пока обе копии живы, память
нужно учитывать для обеих.

Планом, упаковкой, входами и выходами владеет вызывающий код. План должен быть
получен через `query`; менять его поля нельзя. Упаковка относится к создавшему
её плану: одинаковый размер в байтах не делает разные раскладки совместимыми.
План и веса можно разделять между одновременными вызовами с разными выходами.
Исполнение не выделяет память в куче и не упаковывает веса повторно.

M и K должны быть положительными; ноль входных строк допустим. Размеры и шаги
между строками задаются в элементах float. Шаг должен вмещать логическую строку,
в том числе при rows=0. Достаточно обычного выравнивания float. Входы только для
чтения могут пересекаться друг с другом. Выход не должен пересекаться с входным
представлением, промежутками между его строками или планом. Упаковка требует
раздельных исходного и конечного буферов. Переполнение размеров, недостаточная
ёмкость и запрещённые пересечения отклоняются до первой записи.

Этот внутренний API не создаёт потоки. Будущий планировщик сможет делить
проверенные целые плитки столбцов на непересекающиеся диапазоны выходов.
Прямой вызов функции кернела предполагает, что проверки уже выполнены;
обычные вызовы идут через `velri_linear_run`. Общий интерфейс бэкендов
остаётся отдельной частью проекта.

## Замер с проверкой результата

```sh
cmake -S . -B build -DVELRI_BUILD_BENCHMARK=ON
cmake --build build
./build/bench_linear auto 1 1024 1024 1000 21
```

Аргументы: вариант, число входных строк, M, K, повторения на один образец и
число образцов. Необязательный последний аргумент — независимо обоснованный
**арифметический потолок в TFLOPS для этого однопоточного запуска**. Без него
инструмент сообщает, что потолок неизвестен, не придумывая частоту CPU или
ограничение памяти.

Инструмент проверяет каждый выход перед замером и после каждого образца.
Подготовка измеряется отдельно, проверки представлений входят во время вызова.
TFLOPS учитывают полезные `2 × rows × M × K` операций, без дополнения нулями
и преобразований типов. Повторяемые веса могут находиться в кеше. Пул работников
и граф модели здесь не измеряются; [правила измерений](https://github.com/velri-inference/velri/blob/main/docs/RU/performance.md) сохраняются.

Проверки адресов и неопределённого поведения включаются через `VELRI_SANITIZE=ON`;
нужен компилятор с соответствующими библиотеками санитайзеров. На POSIX тесты
также используют защитные страницы и одновременные вызовы с общими весами.
Одного совпадения арифметики недостаточно для проверки границ памяти и владения.

## Проверка распараллеливания GEMV

Для Linux есть отдельный диагностический инструмент с постоянными работниками:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DVELRI_BUILD_PARALLEL_BENCHMARK=ON
cmake --build build
lscpu -e=CPU,CORE,SOCKET,NODE
./build/bench_linear_parallel auto 1024 1024 0,1,2,3 7 normal 16
```

Замените `0,1,2,3` доступными номерами CPU своей машины. Сначала выберите по
одному логическому CPU на физическое ядро, затем попробуйте добавить соседние
SMT-потоки. По одним номерам CPU нельзя надёжно определить, какие потоки делят
ядро. Инструмент проверяет доступность CPU для процесса и отклоняет недоступные
или повторяющиеся номера.

Аргументы: вариант, M, K, список CPU, число измеряемых образцов, режим страниц
`normal|huge` и число проверочных задач. Ноль измеряемых образцов оставляет только
проверки корректности. Каждая проверочная задача меняет вход, чередует наличие
bias и затирает выход перед сравнением с независимым эталоном. Проверяются и
защитные значения вокруг выходного буфера.

Работники используют общие неизменяемые веса FP32, упакованные заранее. Каждый
получает отдельный диапазон целых выходных плиток, поэтому порядок накопления
по K сохраняется для каждого выхода. Вызывающий поток сам обрабатывает один
диапазон. Работников не больше, чем плиток: маленькая матрица не должна запускать
лишних работников из-за длинного списка CPU. Выбранные CPU и фактическое число
работников выводятся в JSON.

Замер включает выдачу работы, арифметику и ожидание завершения. Упаковка,
выделение памяти, создание потоков и начальная проверка представлений происходят
заранее. Между вызовами работники активно ждут: здесь измеряется занятый пул,
а не энергопотребление или пробуждение простаивающего движка. Диагностический
инструмент не является планировщиком движка и не подбирает число потоков сам.

Каждый образец содержит полезные TFLOPS, медиану/p99/максимум задержки вызова,
CPU-время процесса, принудительные переключения контекста и малые страничные
ошибки. Выходы проверяются до и после каждого образца. Повторяйте запуски,
чередуя порядок; учитывайте медленные образцы и длинные задержки наряду с медианой.

`huge` запрашивает transparent huge pages до первого обращения к памяти.
Инструмент читает их размер из Linux и выводит фактические байты `AnonHugePages`
для отображения весов. Успешный запрос не гарантирует выделение. Сравнивайте с
`normal` на той же машине: большие страницы не всегда ускоряют работу.

Необязательный последний аргумент — независимо измеренная скорость чтения в
**ГБ/с** с тем же числом работников и тем же размещением данных в кеше/RAM.
Эквивалент для GEMV с весами FP32: `ГБ/с / 2000` TFLOPS, то есть две полезные
операции на четырёхбайтовый вес. В выводе это поле `read_control_TFLOPS`.
Это измеренный ориентир для сравнения, а не физический потолок. Сам инструмент
его не измеряет и не придумывает значение, если аргумент пропущен. Пропускную
способность целого серверного сокета нельзя подставлять вместо доступной VM.

## Проверка AVX2 на Colab, 10 ноября 2026

Описанные выше изменения AVX2 собраны и измерены в CPU-only Colab VM, которая
показывает AMD EPYC 7B12, четыре физических ядра и восемь логических CPU.
Clang 18.1.3 и GCC 14.2.0 использовали C23, O3 и строгие правила арифметики.
В каждой паре старый и новый кернел собраны одним компилятором: коэффициент
ускорения не является сравнением компиляторов. Старый исходник взят из
`bf9f45b7`. Диагностический пул, packing и выделения памяти одинаковы для обеих
версий. Замер включает раздачу работы и ожидание, но исключает packing,
создание потоков и предварительную проверку API.

Здесь медианы десяти чередующихся пар AB/BA; каждый образец длится не меньше
100 мс после прогрева. Все выходы проверяются побитово до и после замера.
В таблице выбран режим запроса больших страниц; веса 256×256 и 512×512 занимают
меньше 2 МиБ и в этом стенде фактически используют обычные страницы.
Реальное выделение страниц записано, а не выведено из успешного запроса.

| Задача | Компилятор | Работники | До, TFLOPS | После, TFLOPS |
| :--- | :--- | ---: | ---: | ---: |
| GEMV, M=256 K=256 | GCC | 1 | 0,01143 | 0,03583 |
| GEMV, M=1024 K=1024 | GCC | 4 | 0,04249 | 0,08948 |
| GEMV, M=1024 K=1024 | Clang | 4 | 0,10201 | 0,09699 |
| GEMV, M=8192 K=8192 | Clang | 4 | 0,02365 | 0,02349 |
| GEMM, rows=64 M=512 K=512 | Clang | 1 | 0,02788 | 0,04228 |
| GEMM, rows=64 M=512 K=512 | Clang | 4 | 0,09634 | 0,15415 |
| GEMM, rows=64 M=512 K=512 | GCC | 4 | 0,06867 | 0,14923 |
| GEMM, rows=64 M=4096 K=4096 | Clang | 4 | 0,09848 | 0,13835 |

Большой выигрыш GEMV относится к исправлению машинного кода GCC. У GEMV с Clang
нет устойчивого общего ускорения; отдельные малые задачи замедлились. GEMM
существенно ускорился с обоими компиляторами. Эти замеры не доказывают лидерства
на разных CPU.

Независимые контроли дают следующие ориентиры, все выражены в TFLOPS:

| Работники | Чтение 4 МиБ, эквивалент GEMV | Чтение 256 МиБ, эквивалент GEMV | Чистые FP64 FMA |
| ---: | ---: | ---: | ---: |
| 1 | 0,03796 | 0,01150 | 0,05096 |
| 2 | 0,05271 | 0,02022 | 0,10172 |
| 4 | 0,12660 | 0,03119 | 0,20319 |
| 8 | 0,12548 | 0,03464 | 0,20385 |

У контролей чтения подтверждены большие страницы; ГБ/с переведены в эквивалент
GEMV по описанной выше формуле. Они и цикл FMA — измеренные ориентиры, а не
доказанные достижимые потолки GEMV. Физическая полоса RAM, выделенная VM,
неизвестна. Восемь SMT-потоков делят арифметические блоки четырёх ядер; они
не всегда быстрее, а сырые данные сохраняют медленные образцы и длинные задержки.

Отдельное сравнение с PyTorch 2.14.1/MKL 2024.2 использует одинаковый постоянный
пул и разбиение выходов, с однопоточным MKL внутри каждого работника. На четырёх
работниках cached GEMV 1024² даёт 0,09458 TFLOPS у Velri и 0,06948 у PyTorch;
GEMV 8192² — 0,02617 и 0,02852. GEMM 64×512² — 0,15563 и 0,24200.
PyTorch использует арифметику FP32 и не выполняет контракт последовательного
FP64-эталона Velri. Обычные вызовы ATen тоже измерены: их GEMV использовал около
одного CPU даже при запросе четырёх потоков, поэтому такое сравнение включает
различия распараллеливания. Оно не доказывает четырёхкратного ускорения микрокернела.

Итоговые проверки прошли с Clang, GCC, GCC ASan/UBSan, baseline-only Clang и
ARM64 GCC под QEMU. Каждый доступный x86-вариант прошёл 491 680 побитовых сравнений
выходов/защитных значений. Независимый эталон и замороженный fixture не изменены.
AVX-512 собран, но выполнить его на этой VM нельзя. Полная исправленная серия
содержит 39 конфигураций и 1560 измеряемых образцов. Стенд `v2` исправляет ошибку
печати метаданных раннего запуска и проверяет размеры и число работников.
Исходники, хеши, дизассемблирование, сырые образцы, отклонённые варианты и полный
отчёт остаются локально в `docs/benchmarks/avx2-finish-2026-11-10/`, вне Git.

## Предыдущие замеры точных кернелов: Ryzen 9 9950X

Следующие измерения сделаны до описанных выше изменений AVX2.

Парное сравнение запускало новый C-исходник арифметики внутри сохранённого
Rust-стенда с пулом работников на Ryzen 9 9950X. Измерены полные вызовы линейного
слоя с подготовленными весами, а не будущий C runtime. На конфигурацию приходятся
три пары процессов с чередованием порядка, 21 образец на процесс и побитовая
проверка каждого выхода. База — первая **точная C-версия с накоплением в FP64**,
а не более быстрая историческая реализация FP32.

| Задача, 16 работников | Первая точная версия, TFLOPS | Итоговая версия, TFLOPS | Арифметический ориентир FP64, TFLOPS |
| :--- | ---: | ---: | ---: |
| Cached GEMV, M=1024 K=1024, AVX-512 | 0,460 | 0,773 | 2,425 |
| Нечётный GEMV, M=1025 K=1023, AVX2 | 0,173 | 0,538 | 1,287 |
| GEMM, rows=64 M=512 K=512, AVX-512 | 0,497 | 1,133 | 2,448 |
| GEMM, rows=256 M=4096 K=4096, AVX-512 | 0,424 | 1,419 | 2,258 |
| Streaming GEMV, M=8192 K=8192, AVX-512 | 0,0433 | 0,0427 | Предел RAM неизвестен |

Арифметические ориентиры используют показания APERF/MPERF вокруг итоговых
измеряемых циклов: 32 FP64 FLOP/такт/ядро для AVX-512, 16 — для AVX2. Счётчики
относятся ко всему CPU, снимаются не одновременно и включают активность ОС.
Это условные ориентиры для FMA, а не достижимые потолки цикла с преобразованиями,
загрузками и синхронизацией. Streaming-случай немного замедлился; физический
потолок RAM не установлен. Не определяющий его скорость арифметический ориентир
составляет примерно 2,86 TFLOPS.

Сохранённое расширение плитки AVX2 ускоряет cached GEMV, но теряет примерно
2–3% в измеренных контрольных GEMM. В итоговом сравнении cached GEMV на восьми
работниках даёт 0,539 TFLOPS при арифметическом ориентире 1,359 TFLOPS.
Универсального утверждения, что 16 работников или самый широкий ISA всегда
оптимальны, нет.

Отдельный прямой вызов поставляемого C API, закреплённый за одним ядром при
M=64 K=1024, дал 0,0899 TFLOPS. Переданный номинальный арифметический ориентир
0,1824 TFLOPS предполагает 5,7 ГГц на этом ядре; это не измеренная устойчивая
частота. Проверка включает валидацию API и не использует пул работников.

Программное семплирование подтверждает существенные затраты CPU-времени на
координацию и ожидание работников в старом стенде коротких вызовов. Доли семплов
не равны долям задержки. Профилирование аппаратных событий было недоступно
(`perf_event_paranoid=4`). Отдельный контроль чтения через XOR сохранён, но
не выдаётся за физический потолок памяти. Исходные данные, снимки кода,
дизассемблирование, профили, хеши бинарников и отклонённые либо некорректно
поставленные сравнения остаются локально в
`docs/benchmarks/linear-bottlenecks-2026-11-10/`, вне Git.
