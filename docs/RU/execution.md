# Подготовка, память и гибридное исполнение

[English](../EN/execution.md)

Этот документ описывает модель исполнения в `Velri-lib`: что происходит при подготовке плана, как взаимодействуют CPU и Vulkan, как синхронизируется память и как обрабатываются ошибки и отмена. Общая структура библиотеки — в [architecture.md](architecture.md), система кернелов — в [kernels.md](kernels.md).

**Статус:** базовое ядро исполнения (`velri_plan_prepare`, упаковка `scratch`, DAG-анализ и элизия барьеров, обмен через RAM, общие WEIGHT-слабы между планами через `share_weights_from`, общие STATE-арены между слотами через `velri_slot_create_shared_state`, захват и переиспользование командных буферов decode в Vulkan с бакетированным FlashDecoding Split-KV, дренаж завершений и отмена) реализовано и покрыто тестами на CPU, `mock_async` и опциональном Vulkan ([architecture.md](architecture.md)); timeline semaphores, `synchronization2` и дисковый staging (PLE) — последующие этапы.

## 1. Подготовка (`prepare`) против шага исполнения

Всё неизменяемое выносится из цикла генерации токенов:

| Делается один раз в `prepare` | Делается на каждом шаге |
| :--- | :--- |
| Валидация графа, форм, типов, шагов и доступов к состоянию | Проверка динамических границ (число токенов, позиции, маршруты MoE) |
| Запрос поддержки операций (`query_operation`) у разрешённых устройств | Заполнение компактных динамических параметров в слоте исполнения |
| Выбор размещения, AOT-кернелов, раскладок и явных передач/преобразований | Отправка подготовленных заданий бэкендам (`submit`) |
| Расчёт полного бюджета памяти и резервирование буферов/слотов | Ожидание завершения (`wait`) и передача результата вызывающему коду |
| Однократная упаковка неизменных весов и создание GPU pipelines / descriptors | `0 B` аллокаций в куче, никакого разбора JSON и поиска по именам |

План хранит длину каждого пакета операций на одном устройстве и индекс для захвата команд. Передача данных завершает пакет. Создание и запуск слота используют сохранённые границы. Для бэкенда без пакетной отправки каждый пакет содержит одну операцию.

Если неизменяемые веса после упаковки больше не нужны в исходном формате, исходный буфер освобождается явно. Пока живы оба представления, в бюджет памяти входят оба.

### Бюджет памяти и UMA
В бюджет входят все одновременно живущие объекты: исходные и упакованные веса, состояние сеансов, рабочая память `scratch`, staging-буферы, выравнивание и фактический резерв аллокатора (например, VMA). Память драйвера без достоверного отчёта отмечается как **неизвестная**.

На системах с общей физической памятью (**UMA**, включая встроенную графику и Android) CPU и GPU делят один запас RAM: нельзя складывать host-visible и device-local как два независимых объёма памяти.

## 2. Гибридное исполнение CPU + Vulkan

Базовый маршрут обмена между любыми двумя бэкендами проходит через обычную память CPU:

```text
ресурс устройства A  ──►  согласованный буфер в RAM (staging)  ──►  ресурс устройства B
```

- Копирование байтов само по себе не меняет внутреннюю раскладку данных: если формат закрыт для другого бэкенда, `prepare` добавляет явное поддержанное преобразование либо отклоняет размещение.
- Буфер staging нельзя переиспользовать, пока не завершились все потребители его данных; слоты отслеживаются по конкретным идентификаторам принятой работы, а не по номеру слоя модели.

### Типовой гибридный путь (например, MoE-эксперты на CPU, attention на Vulkan)
1. Vulkan-бэкенд вычисляет маршруты роутера и входные активации, копирует их в доступный хосту staging-слот и сигнализирует о завершении записи.
2. CPU-бэкенд дожидается готовности и видимости данных, после чего пул `velri_pool` выполняет выбранных экспертов по подготовленным диапазонам.
3. CPU завершает запись (при необходимости выполняя `flush` для некогерентной памяти), данные передаются обратно на GPU, а зависимый `dispatch` ждёт окончания передачи.
4. Staging-слот освобождается для переиспользования только после завершения последнего потребителя.

### Диск как источник данных
Для крупных таблиц на диске (например, таблица n-грамм PLE; см. [qwen4_exp.md](../../../docs/RU/models/qwen4_exp.md)) используется ограниченный буфер staging с явной зависимостью между загрузкой/декодированием строк и первым вычислительным потребителем. Файловый ввод-вывод абстрагируется в платформенном слое; при замерах диска отдельно учитывается кэш ОС.

## 3. Синхронизация и память Vulkan

- **Базовый уровень — Vulkan 1.1:** для ожиданий хоста используются `VkFence`, для зависимостей между очередями — binary `VkSemaphore`, внутри очереди — точные memory/execution barriers.
- **Расширения по проверке:** `timeline semaphores` (Vulkan 1.2 / `VK_KHR_timeline_semaphore`) и `synchronization2` включаются только при подтверждённой поддержке устройством.
- **Без антипаттернов:** `vkQueueWaitIdle` после каждой операции запрещён как общий механизм исполнения; один объект завершения отслеживает целый пакет команд, а не каждый отдельный `dispatch`.
- **Отображённая память (`HOST_VISIBLE`):** само свойство `HOST_VISIBLE` не гарантирует максимальную скорость ни для CPU, ни для GPU. Для некогерентной памяти обязательны `flush`/`invalidate` с учётом `nonCoherentAtomSize`. Даже на UMA и когерентной памяти обычные C-атомики и `volatile` **не заменяют** барьеры и протокол видимости Vulkan.
- **Прямой доступ и zero-copy:** отказ от копирования на UMA или прямое чтение `HOST_VISIBLE` дискретным GPU — отдельные режимы, которые выбираются только по свойствам памяти и результатам измерений.
- **Повторное использование команд:** буферы команд переиспользуются только при совместимых привязках ресурсов и соблюдении времени жизни изменяемых слотов (повторное использование командных буферов Vulkan не обещает семантики CUDA Graphs).

## 4. Завершение, ошибки и отмена

Первая версия публичного шага в движке — **синхронная** для вызывающего приложения, но внутри шага бэкенды могут исполнять пакеты асинхронно через объекты завершения (`poll` / `wait`). Перед возвратом из шага все принятые работы и передачи выходных данных должны быть завершены.

### Правила безопасности ресурсов
1. **Отказ до принятия (`submit` вернул ошибку без принятия работы):** устройство ничего не запустило и не удерживает переданные буферы.
2. **Ошибка после принятия части работы:** бэкенд всё равно возвращает объект завершения для уже запущенных обращений к памяти; рантайм обязан дождаться их окончания до освобождения или переиспользования буферов.
3. **Отмена во время шага:** рантайм прекращает отправку новых заданий и дожидается завершения уже принятых. Принудительное прерывание выполняющегося кернела от бэкенда не требуется.
   - Отмена до принятия первой работы шага оставляет прежнее состояние сеанса нетронутым.
   - Отмена после принятия работы (или ошибка, способная затронуть состояние) переводит сеанс в состояние, требующее явного `reset` перед продолжением; автоматический откат частичного шага в первой версии не обещается.
   - Отмена, пришедшая после фиксации успешного результата шага, не отменяет готовый результат.
4. **Потеря устройства (`VK_ERROR_DEVICE_LOST`):** выполняется процедура остановки и очистки бэкенда; связанные ресурсы не переиспользуются до подтверждения безопасного освобождения, а затронутые сеансы помечаются как ошибочные.
