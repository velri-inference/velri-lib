# Архитектура кернелов: Slang-first (`slangc` AOT для GPU и CPU)

[English](../EN/kernels.md)

Вместо раздельного сопровождения GLSL-шейдеров, `#ifdef`-комбинаций и дублирующихся ручных SIMD-файлов под каждую архитектуру CPU целевая система кернелов `Velri-lib` строится вокруг **Khronos Slang** (`Apache-2.0 WITH LLVM-exception`) с **чистой AOT-компиляцией через `slangc` при сборке**.

**Статус:** активная реализация в `velri-lib/src/kernels/slang/`. `slangc` обязателен при сборке `VelriLib::velri` (23 CPU MatOps-кернела поверх `velri_pool`, включая FP64 linear), а опция `-DVELRI_ENABLE_VULKAN=ON` добавляет 29 модульных SPIR-V 1.6 шейдеров в `src/kernels/slang/vk/` (плюс 6 шейдеров калибровки потолков в `tools/vk_ceilings.slang` только при `VELRI_BUILD_BENCHMARKS=ON`). Прежний ручной C23/SIMD-код сохранён для исторических сравнений на ветке `archive/c23-cpu-legacy`.

---

## 1. Главные принципы: переиспользование компонентов и никаких дублей

1. **Маленькие переиспользуемые компоненты вместо монолитных копий:** общая математика раскладывается на интерфейсы и дженерики Slang (`IElement`, `IActivation`, `IEpilogue`, `IKVSource`, общие редукции). Одна реализация `RMSNorm`, `RoPE`, `GatedMLP` или `Linear` переиспользует эти компоненты вместо копипасты.
2. **Не плодим почти одинаковые кернелы:**
   - **Никаких отдельных исходников для AVX2 и AVX-512** (или для `F32`/`F16`/`BF16`): один параметризованный `.slang`-модуль AOT-компилируется `slangc` под нужные целевые профили (`base`, `avx2`, `avx512`, `aarch64`, `riscv64`, `spirv`).
   - Аппаратные отличия (например, редукция по подгруппе на GPU против скалярного/векторного цикла на CPU, или `CoopMat` на GPU) изолируются внутри тонких низкоуровневых примитивов, а не размножают целые кернелы.
3. **Чистый AOT (`slangc` при сборке) — `0` компиляторов в рантайме:** готовый бинарь Velri не зависит от `libslang`, LLVM, `shaderc`, Python или PyTorch.

```text
src/kernels/slang/
  ├── common/ (numeric, activations, epilogue, reductions)
  └── ops/    (norm, rope, elementwise, linear, ...)
        │
        ├──► slangc -target spirv      ──► .spv (+ spirv-val)       ──► Vulkan-бэкенд
        ├──► slangc -target llvm-ir/o  ──► .o (ISA-варианты CPU)    ──► CPU-бэкенд (velri_pool)
        └──► slangc reflection         ──► таблицы привязок CMake
```

## 2. Модульная композиция в Slang

Принципы композиции Velri выражаются напрямую в типах Slang, без ветвлений по имени модели:

- **`IElement` (`common/numeric.slang`):** единый доступ к `F32`, `F64`, `FP16`, `BF16`, `INT8` (загрузка/преобразование в накопитель и запись обратно) — операции не дублируются по типам.
- **`IActivation` (`common/activations.slang`):** `SiLU`, `GELU_tanh`, `ReLU2`, `Identity` (+ опциональный симметричный `clamp`) — переиспользуются одновременно в standalone-активациях, `GatedMLP` и эпилогах `Linear`.
- **`IEpilogue` (`common/epilogue.slang`):** добавление `bias`, масштабирование (`W8A8` / `W8A32`) и опциональная активация — общие для `GEMV` и `GEMM` на CPU и GPU.
- **`IKVSource`:** источник ключей и значений для attention — раздельные буферы, общий буфер или восстановление на лету `K = RoPE(V * w_k)` (Gemma 4) без лишнего буфера `K`.
- **AOT-слияния (fusion):** горячие связки (`Residual + RMSNorm`, `GatedMLP`, `Linear + Epilogue`, `K=V + Attention`) собираются как AOT-специализации тех же интерфейсов из контролируемого манифеста CMake.
- **Autodiff (`bwd_diff`):** встроенная возможность Slang, доступная при необходимости для будущих инструментов квантования/калибровки без переписывания математики.

## 3. GPU-путь: Vulkan / SPIR-V и переносимость на другие GPU

- **Базовый профиль:** Vulkan 1.1 compute со стандартными storage buffers и явной проверкой возможностей устройства до выбора кернела.
- **Ускоренные пути (SPIR-V 1.5/1.6):** `linalg::CoopMat` (`SPV_KHR_cooperative_matrix`, FP16/BF16/INT8), `VK_KHR_shader_bfloat16`, `VK_KHR_shader_float16_int8`, `VK_KHR_shader_integer_dot_product` и subgroup-операции включаются **только при подтверждённой поддержке устройством**.
- **Раздельные проверки возможностей:** хранение, арифметика и накопление проверяются независимо; фиксированный размер subgroup (32 или 64) не зашивается как допущение.
- **Валидация при сборке:** каждый `.spv` проверяется `spirv-val` под целевой профиль Vulkan в CMake и CI.
- **Управление pipelines:** выбор AOT-специализаций и создание `VkPipeline` происходят в `prepare`; совместимость дискового pipeline cache проверяется по устройству и драйверу.
- **Переносимость на будущие GPU API:** те же `.slang`-модули в перспективе компилируются в **Metal (MSL)**, **CUDA**, **DXIL** и **WGSL** за тонкими device-бэкендами в `src/backend/<name>/` без переписывания математики.

Все рабочие модули SPIR-V используют `shaderInt64` для арифметики адресов. Бэкенд проверяет поддержку этой возможности при перечислении устройств и включает её при создании устройства. При сборке Vulkan Slang выдаёт описание параметров каждой рабочей точки входа. По нему CMake формирует C-структуры push constants с проверкой размера и смещения каждого поля во время компиляции.

Для F32-чанков из 3–16 строк выровненное ядро повторно использует вектор весов для четырёх входных строк. Для 17–64 строк при выровненных входах и K, кратном 16, выходной тайл имеет размер 64×64, а два буфера поочерёдно хранят тайлы шириной 16 по K. Split-K может распределить внутреннее измерение между группами и добавляет bias после редукции.

На подгруппах из 32 линий выровненный F32 prefill использует тайловый online softmax. От 128 строк запроса ядро FlashAttention загружает K/V один раз на четыре запроса при размерности головы 32 или 64 и на два запроса при размерности 128. Размер тайла составляет 256 и 64 ключа соответственно. Четыре подгруппы объединяют частичные максимумы, суммы весов и взвешенные значения в 8320 байтах общей памяти рабочей группы. Оценки остаются в регистрах, буфер квадратного размера по длине последовательности не требуется. Для меньших чанков доступно построчное ядро с тайлами по 64 ключа. Обе реализации учитывают causal-маску и скользящее окно каждого запроса. [FlashAttention, Dao и др.](https://arxiv.org/abs/2205.14135)

В F32-prefill с планом не более чем на 64 строки, 32–64 активными запросами, размерностью головы 64 и хотя бы 256 видимыми ключами устройства с подгруппами по 32 потока могут делить KV на восемь частей или меньше. Рабочая группа читает плитку из 32 ключей и значений для 32 запросов. Второй запуск объединяет максимумы, суммы весов softmax и взвешенные значения частей. Общий буфер устройства занимает 68 элементов F32 на голову запроса и часть KV, с ограничением 32 МиБ. Нужны выровненные Q и KV и 16,5 КиБ общей памяти рабочей группы. При других раскладках или нехватке дополнительного буфера используется обычное ядро prefill.

При плотном префилле от 512 строк и размерности головы 64 бэкенд может использовать каждый тайл KV для 16 соседних запросов и писать нормализованный результат сразу в выходной тензор. Путь F32 использует тайл из 32 ключей в общей памяти группы. В прямом F32-ядре четыре линии подгруппы вычисляют одно 64-мерное скалярное произведение. Суммы весов softmax объединяются после последнего тайла. Для F16 KV устройство с поддержкой кооперативных матриц FP16, накоплением в F32 и общей памятью от 32 КиБ обрабатывает 256 ключей за итерацию группы. Запросы и веса softmax раскладываются на две части FP16. Второе матричное произведение учитывает ошибку округления первой части. Softmax, накопление и итоговая нормализация выполняются в F32. Оба ядра поддерживают causal attention и окна от 512 позиций, временные данные остаются внутри рабочей группы.

При F16 KV флаг `attr.attention.allow_f16_matmul` разрешает округлять нормализованные по строкам запросы и веса softmax до binary16 для QK и PV. Оба произведения и softmax накапливаются в F32. Кооперативное ядро KHR работает от 128 строк запроса, а при истории от 256 позиций — от 64 строк. Если устройство поддерживает редукции, преобразования и поэлементные операции над матрицами подгруппы из `VK_NV_cooperative_matrix2`, то при плотном causal attention чанк от 512 строк после 1024 позиций может использовать каждый фрагмент K и V для двух тайлов по 16 запросов. Пока подгруппа считает softmax, она может загружать V текущего тайла и K следующего. Накопленные в F32 веса суммируются по столбцам один раз на строку после обхода KV. Для этого нужны число строк и ёмкость KV, кратные 32, 48 КиБ общей памяти рабочей группы и выровненные 64-мерные головы. Для остальных подходящих форм при подготовке остаётся доступным ядро KHR.

При однотокенном F32 attention на подгруппах из 32 потоков выровненные K/V с одинаковой размерностью голов 32, 64 или 128 позволяют поручить каждой рабочей группе восемь выходных каналов. До 256 ключей включительно группа вычисляет оценки своей головы и свою часть взвешенной суммы V. При совпадении Q с выходом бэкенд выбирает одну группу записи на голову или отдельную редукцию Split-KV. На длинном контексте Split-KV вычисляет частичные максимумы, суммы весов и взвешенные значения V, затем объединяет их с устойчивым пересчётом softmax. Для prefill и других раскладок действуют собственные правила выбора ядра.

При длинном однотокенном декоде с KV в binary16 и размерностью голов 64 одна рабочая группа Vulkan может читать каждую строку K/V сразу для трёх или четырёх Q-голов, использующих одну KV-голову. От 4096 видимых ключей движок выбирает 64 секции при недостатке рабочих групп в сетке. Проверяются подгруппы по 32 потока, выравнивание адресов и шагов по 16 байтам, наличие шейдеров и объём временной памяти. Отдельная редукция в F32 объединяет 64 частичных результата. Для более коротких контекстов используются ранее записанные команды с меньшим числом секций.

При записи Vulkan-команд бэкенд может объединить соседние плотные F32-проекции однотокенного графа. Q/K/V совмещаются с RoPE по двум половинам всей головы и записью в KV-кэш, gate/up — с SiLU и умножением, выходная проекция — со сложением residual. Предшествующий взвешенный RMSNorm для выровненной строки длиной до 2048 может выполняться в той же рабочей группе. Группа с индексом ноль сохраняет нормализованную строку, а проекции записывают все наблюдаемые выходы исходного графа. Проверка физических диапазонов исключает пересечения, способные вызвать гонку. Для остальных форм тензоров, шагов и размеров подгруппы бэкенд записывает исходные операции.

## 4. CPU-путь: Slang-first и план доработок Slang CPU-бэкенда

### Роль Slang и C23 на CPU
Целевой курс для CPU — **Slang-first для всех оптимизированных кернелов** из общей модульной базы. На чистом **C23** остаются:
- публичный API, граф, планировщик памяти и реестр бэкендов;
- постоянный пул рабочих потоков `velri_pool` и L3-планировщик;
- **простые независимые C23-эталоны** для проверки корректности без участия компилятора Slang.

### Ограничения Slang CPU из коробки и стратегия доработок
Slang умеет выдавать CPU-код через LLVM (`slang-llvm`: LLVM IR / `.o`) и C++. На практике мы учитываем реальные ограничения:
1. В C++-бэкенде нет workgroup-барьеров (`GroupMemoryBarrierWithGroupSync`) и пользовательских атомиков — алгоритмы с `groupshared`-синхронизацией напрямую на CPU не переносятся.
2. Стандартная C++-обвязка слишком тяжела для коротких вызовов из C23 `velri_pool`; для CPU нужен прямой путь через **LLVM IR / `.o` с чистым C-ABI** и `0 B` аллокаций в куче.
3. Один и тот же Slang-исходник компилируется в целевой LLVM IR, а затем **флагами таргета компилятора** (`-march=x86-64`, `-mavx2 -mfma -mf16c`, `-mavx512f -mavx512bw ...`, `aarch64`, `riscv64`) получаются ISA-варианты — **без копирования кода под AVX2 и AVX-512**.
4. Для горячего CPU `GEMM` / `GEMV` критичны регистровый тайлинг, перепаковка панелей в `scratch` и аппаратные dot-инструкции (`vdpbf16ps`, `vpdpbusd`). Если стандартный CPU-бэкенд Slang не вытягивает нужный кодген, мы фиксируем конкретный разрыв по замерам и точечно дорабатываем CPU-бэкенд Slang (чистый C-ABI, `fp16`/`bf16`, векторные примитивы / интринсики).

### Проверенные результаты и ограничения Slang `2026.22.1`
Slang CPU всегда собирается в составе `VelriLib::velri` (`entry_cpu.slang`); Vulkan включается опцией `-DVELRI_ENABLE_VULKAN=ON` (`vk/*.slang`), и оба бэкенда проверяются сквозным тестом `test_kernels` (опциональные `bench_slang_cpu`/`bench_vulkan` собираются при `-DVELRI_BUILD_BENCHMARKS=ON`). На `slangc 2026.22.1` подтверждены оба целевых пути из общих модулей `common/`:
- **CPU (`VELRI_SLANG_CPU_MODE=AUTO|LLVM_IR|OBJECT`):** чистый C-ABI (`[DllExport] export __extern_cpp`) без runtime-зависимостей; единый исходник `linear_cpu.slang` компилируется под любые ОС и архитектуры без дублей.
  - **Основной путь (`LLVM_IR`, по умолчанию для совместимого Clang):** `slangc -target llvm-ir -O0 -fp-mode fast` выдаёт платформо-независимый LLVM IR, [strip_ll_target.cmake](../../cmake/strip_ll_target.cmake) очищает хостовые `target datalayout` / `target triple`, а сам CMake-компилятор (`Clang`) понижает `.ll` → `.o`/`.obj` с флагами целевого тулчейна. Это убирает хардкод ОС и CPU-архитектур и открывает **Linux (x86-64, AArch64, RISC-V 64 / RVV 1.0)**, **Windows (x86-64, ARM64)**, **Android (`arm64-v8a`, `x86_64`)** и **macOS** из одного исходника.
  - **Автоматический fallback (`OBJECT`, для GCC и старых версий Clang):** при конфигурации CMake выполняет короткую пробу `.ll`; если компилятор не принимает LLVM IR версии `slangc` (например, GCC или Clang 18 при `slang-llvm` на базе LLVM 21), `AUTO` автоматически переключается на прямое `slangc -target host-object-code -llvm-target-triple` (поддерживает x86-64 и AArch64 в официальном релизе `libslang-llvm.so`).
  - Ключевые приёмы под LLVM:
    - `pack_b` через `IElement::load4F32` + выровненные записи `Ptr<float4>`/`Ptr<double4>` (убирает `vgather`/`vscatter`), плюс zero-copy чтение `A` для нативных `F32`/`F64` (убирает `call memcpy` от `LoopIdiomRecognize`);
    - программный IEEE-754 `ElemF16` (`-DVELRI_SOFT_F16=1`) на базовом профиле без аппаратного F16C/fcvt — полностью устраняет внешние libcall `__extendhfsf2`/`__truncsfhf2` (критично для Windows MSVC и RISC-V `rv64gc`);
    - переносимый W8A8 GEMM на микрокернеле `F32` накапливает точные суммы по модулю $2^{32}$ при `KC=128` ($|\sum| \le 2^{21} \ll 2^{24}$);
    - одноцикловые редукции через `select(v > m, v, m)` (обычные `max()` и `?:` генерируют `vucomiss` и ломают векторизацию; `select` даёт 4-way ZMM `vmaxps`), Radix-4 Stockham ping-pong для FWHT без алиасинга и запись в локальные буферы строго через `Ptr`.
- **Vulkan (`-target spirv -profile spirv_1_6 -fvk-use-c-layout -O3`):** под C-layout Slang по умолчанию ставит `Aligned 4` на BDA-указатели (`4× LDG.32`), поэтому критичны явные хелперы `OpLoad`/`OpStore Aligned 16` (`LDG.128`/`STG.128`), `ks=0 / BAR / STS.128 + ks=1` перекрытие для однобуферного `CoopMat` (`20 KiB` -> `2 WG/SM`) и `Split-K` (`vk_splitk_reduce`) для малых батчей `F32`.
- **Оставшиеся ограничения `slang-llvm` `2026.22.1` (фронт доработки CPU-бэкенда Slang):**
  1. **`BFloat16` не поддерживается на LLVM-таргете** (`InternalError: Unsupported type for LLVM target!`) — используется побитовый `ElemBF16` (`uint16_t`), без генерации `vdpbf16ps` (`AVX512_BF16`).
  2. **`dot4add_i8packed` и целочисленный dot на CPU не опускаются в `vpdpbusd` (`AVX512_VNNI`)**. Для W8A8 GEMM на AVX-512 VNNI ядро `w8a8_vnni.slang` вызывает LLVM-интринсик напрямую. Оно упаковывает панели row-major весов во время операции и считает тайл 14×32 с накоплением в INT32. Диспетчер проверяет VNNI отдельно от AVX-512. Путь GEMV обслуживает батчи из 1–3 строк.
  3. **В официальном релизном `libslang-llvm.so` собраны только LLVM-бэкенды `X86` и `AArch64`:** в режиме `OBJECT` (с GCC) таргеты вроде `RISC-V 64` недоступны; для них используется штатный путь `LLVM_IR -> Clang` (см. [riscv64-linux-gnu.cmake](../../cmake/toolchains/riscv64-linux-gnu.cmake)), где Clang сам компилирует `.ll` в `rv64gc` / `rv64gcv` (RVV 1.0).

### Критерии приёмки новых Slang-кернелов
Каждый новый или оптимизированный Slang-кернел принимается только после того, как:
- проходит верификацию против независимого C23-эталона (`tests/cpu/typed/reference.c`), ASan/UBSan и проверку ISA-диспетчера (`Nehalem`/`Haswell` под QEMU, а для GPU — `spirv-val`);
- подтверждает измеренную скорость относительно физического потолка устройства по [правилам измерений](../../../docs/RU/performance.md).

## 5. Численные контракты и верификация

- **Валидация до первой записи:** размеры, шаги, переполнения, выравнивание и запрещённые пересечения проверяются до изменения выхода; `rows == 0` ничего не пишет.
- **Нулевые аллокации на горячем пути:** рабочая память `scratch` запрашивается в `prepare`.
- **Вещественные операции (`F64`, `FP32`, `FP16`, `BF16`):** разрешены FMA, несколько аккумуляторов, блочные редукции и полиномиальные приближения; побитовое совпадение между ISA и CPU/GPU не требуется — проверяются явные допуски против C23-эталона.
- **Целочисленные и точные операции (`INT8`, индексы):** детерминированный контракт (`INT8 Linear` накапливает по модулю $2^{32}$ без signed-overflow UB).
- **Защита границ и валидация:** независимый C23-эталон + ASan/UBSan + `guard pages` для CPU-кода; `spirv-val` + Vulkan API/sync validation layers для GPU.

Линейная операция с F32-тензорами может разрешить операнды binary16 через `attr.linear.allow_f16_matmul`. На совместимом Vulkan-устройстве проекции от 64 активных строк используют кооперативные матрицы с тайлом 64 × 64. Ядро преобразует значения при загрузке тайла, накапливает и записывает результат в F32. Дополнительная копия весов в памяти устройства не требуется. При выключенном флаге сохраняется арифметика F32.
